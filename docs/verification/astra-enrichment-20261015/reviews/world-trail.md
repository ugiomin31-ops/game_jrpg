# World trail — 후속 독립 정적 리뷰

- 요청 모델/effort: gpt-6-astra / high, Fast/priority 요청. 실제 모델·effort·tier는 독립 런타임 메타데이터가 없어 확인된 값으로 주장하지 않는다.
- 최초 확인 시 fixes/town-follow-trail.md와 확인한 대체 world 수정 노트는 없었다. 기다리지 않고 완성된 클래스 형태의 TownWorld.cs(645줄)와 GameUI.cs(377줄)를 직접 읽었다.
- 범위: 용량 256, 각 추종자의 경로 간격, 초기 생성/로스터/의상 교체, 모서리 구간, GameUI 실행 순서. 지정된 이 보고서만 작성했다. 소스 수정·Unity·테스트·빌드·브라우저·하위 에이전트 실행 없음.
- **결론: 이 소스 스냅샷에서 확정할 수 있는 신규 결함은 찾지 못했다.** 기존 두 리뷰 항목은 실제 이동 경로 기록과 GameUI의 명시적 실행 순서로 대응됐다. 다만 아래와 같이 버퍼 포화의 정상 해소와 충돌로 막힌 추종자의 복구는 구분해야 한다. 런타임 수용 통과 판정은 아니다.

## 1. 256점 한도와 리더 정지

근거: TownWorld.cs:30-72,405-429,435-469.

- 배열은 고정 256칸이고 Append는 빈 공간 없이 점을 덮어쓰지 않는다. Count가 256을 넘는 경로도 보이지 않는다. 전진하는 일직선 구간만 끝점을 합치므로 긴 직선 이동은 점 수를 계속 늘리지 않는다.
- 리더는 첫 추종자의 trail이 가득 차면 이동하지 않는다(:405,409,422). 이 정지는 존재한다. 이를 “리더는 절대 멈추지 않는다”로 승인하면 안 된다.
- 리더가 멈춘 프레임에도 UpdateFollowers는 실행된다(:383-391). 각 추종자는 자신의 trail이 아니라 **자기 뒤 추종자의** trail 여유로 움직임이 제한된다. 마지막 추종자는 index >= followers.Count라 이 제약을 받지 않는다. 따라서 전원이 가득 차 있어도 마지막부터 점을 소비하고 앞쪽으로 공간이 돌아오는 경로가 있다.
- Count <= 223일 때 목표 간격은 0.95다. 224부터 간격을 줄이고 255 이상에서는 0이 된다(:451). 가득 찬 경로가 짧아서 평소 0.95 간격 때문에 소비를 못 하는 순환 대기는 피한다. 고주사율/느린 입력만으로 영구 정지한다고 볼 근거는 찾지 못했다.
- 이동 시간은 0.1초로, 이동 하위 구간은 0.1로, 추종 반복은 프레임당 32회로 제한된다. Arrive도 같은 반복 예산을 쓰므로 대량의 아주 짧은 점을 한 프레임에 모두 비우지 않을 수 있지만 이후 프레임으로 진행한다.

**남는 한계:** 마지막 추종자가 실제 충돌 때문에 첫 미도달 점까지 끝내 가지 못하면 공간을 소비할 수 없다. 그 상태에서 앞사람들이 충분히 움직여 후속 경로가 차면 정지가 리더까지 전파된다. 막힘 타이머/별도 복구 경로는 없다. 현재 정상 저작 경로에서 이 상태가 발생함을 재현하지 않았으므로 구체적 신규 회귀로 보고하지 않지만, “256점이라 어떤 상황에서도 리더 정지 없음”도 입증하지 않는다. 부모의 분수 모서리/긴 추종/강한 방향 전환 실행 확인에서 리더가 자유롭게 걸을 공간이 있는데도 지속 정지한다면 이 경로를 먼저 확인해야 한다.

## 2. 각 추종자의 경로와 간격

근거: TownWorld.cs:22-27,233-255,407-415,438-466.

- FollowerMotion마다 별도의 FollowTrail이 있다. MoveMember(index)는 이동 후 실제 컨트롤러 위치를 followers[index]에 기록한다. 즉 첫 추종자는 리더, 둘째는 첫 추종자, 셋째는 둘째가 지나간 위치를 따른다. 모두 리더의 전역 heading을 향해 잘라 가던 계산은 없어졌다.
- 남은 거리 계산은 현재 위치부터 첫 경유점까지의 수평 거리 + 큐 내부 경로 길이다(:461). 정상 상태의 간격은 각 선행자와의 **경로상** 약 0.95이며, 모서리에서의 직선거리나 전원 고정 좌표 간격을 보장하는 것이 아니다.
- 초기 배치는 0.9 간격(:170)이고 새로 추가된 슬롯은 앞 슬롯 위치에서 시작할 수 있다(:168-169). 정지 상태에서 즉시 0.95로 벌어지는 방식은 아니다. 이동하며 간격을 만든다.
- 용량 압박 시 의도적으로 간격이 0까지 줄어들 수 있다. 파티 내부 충돌은 IgnoreCollision으로 제외하므로 이 간격 축소가 자기 파티의 물리 차단을 만드는 경로는 보이지 않는다.

## 3. 초기 생성·로스터·의상 교체와 오래된 컨트롤러 참조

근거: TownWorld.cs:159-181,202-255,259-283,481-498.

- 최초 생성 시 새 슬롯에만 Trail.Reset(선행자 위치)를 호출하고, 모든 슬롯에 새 Body와 LastPosition을 설정하며 추종자의 VerticalSpeed를 0으로 만든다.
- RefreshRoster는 기존 포즈를 슬롯별로 보존하고 기존 모델을 비활성화한 뒤 재생성한다. 필요 없어진 후속 슬롯은 RemoveRange로 제거한다. 유지되는 슬롯의 미방문 경로를 보존하므로 메뉴에서 파티를 바꿨다고 미완료 모서리 경로를 지우지 않는다.
- AttachFollowerController는 유지되는 motion 객체에서도 Body를 새 컨트롤러로 교체한다(:249-250). 활성 상태인 다른 컨트롤러만 IgnoreCollision 대상으로 삼는다. 오래된 비활성 Body가 이동에 계속 쓰이는 경로는 찾지 못했다.
- 의상 교체는 같은 위치/회전에서 모델을 바꾸고 동일한 재연결을 수행한다. 리더의 컨트롤러가 교체되면 살아 있는 추종자들과 IgnoreCollision을 다시 설정한다. 리더의 수직 속도는 의상 교체만으로 지워지지 않지만 위치를 유지하므로 이를 이번 변경의 결함으로 보지 않았다.
- 기록한 위치에서 0.1보다 크게 외부 이동한 경우 경로와 수직 상태를 재설정한다(:483-497). 이는 오래된 경로 폐기이며 장애물 반대편으로 임의 재배치된 상태의 안전한 새 경로 탐색까지 제공하는 것은 아니다.

## 4. 모서리 구간

근거: TownWorld.cs:45-65,74-75,426-429,452-466.

- 방향 반전이나 각도가 있는 모서리는 큐에 남긴다. 전진 방향이 같고 정규화 외적 제곱이 1e-8 미만인 사실상 직선만 합친다.
- 추종자는 큐의 First부터 소비하고, 첫 점을 건너뛰어 선행자의 현재 위치로 직접 이동하지 않는다. 0.015 도착 허용 거리 안에서 다음 구간으로 넘어가므로 경로는 수치상 근사다.
- 리더와 추종자 모두 CharacterController.Move의 짧은 구간으로 움직이고 실제 결과를 후속 큐에 기록한다. 추종 중 transform.position 순간 이동은 없다.
- 위치 경로만 복사하며 물리 접촉 상태까지 복사하지는 않는다. 실제 import된 충돌체/스킨 폭에서 모든 모서리가 영원히 막히지 않는다는 증명은 이 소스 리뷰에 포함되지 않는다.

## 5. GameUI 실행 순서와 같은 프레임 입력

근거: GameUI.cs:13-15,246-279,362-368; TownWorld.cs:362; DungeonWorld.cs:432-436,533-536; UIInput.cs:112-115.

- GameUI에 DefaultExecutionOrder(-100)이 추가됐다. GameUI 및 두 월드 .cs.meta에는 별도 executionOrder가 없고, 두 월드 클래스에도 다른 실행 순서 지정이 없다. 전역 pause/map 입력은 기본 순서 월드 Update보다 먼저 처리된다.
- W를 누른 채 Tab/Escape/M으로 메뉴·지도를 여는 경우 GameUI가 Consume 및 pause를 설정한 뒤 월드가 이를 확인하는 순서다. 이전 world-input 리뷰의 전역 메뉴 열림 순서 불확실성은 소스상 해소됐다.
- 메뉴 닫힘은 기존 차단 상태 또는 같은 프레임 Consume로 계속 보호된다.
- 공개 DungeonWorld 액션에는 ConsumedThisFrame 검사를 추가하지 않았다. HUD가 Consume 후 공개 액션을 호출하는 기존 경로도 유지한다.
- 이 속성이 모든 EventSystem/HUD 콜백을 무조건 월드보다 먼저 실행시키는 것은 아니다. 키보드 전역 메뉴 순서의 수정과 포인터/HUD 전체 중재를 동일하게 주장하지 않는다.
